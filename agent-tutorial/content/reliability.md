## 把“能演示”变成“能长期使用”

可靠性来自多条边界共同成立：模型请求可重建、动作权限可判断、失败有分类、任务能停止、产物可验证。不要仅优化一次成功演示。应该问：十次相同任务是否稳定？断网时发生什么？用户取消后还会不会继续改文件？恢复时会不会重复提交？

对 RIVER-Agent，可靠性首先意味着交通结论可追溯且不越过岸基辅助决策边界。dsh 提供的会话、工具执行和调度能力可以作为 Harness 基础；业务 Run 状态、领域时效检查、World State 与 Result Store 仍要按项目契约设计。这一篇的数字、阈值与状态结构都是教学建议，需要用真实任务校准。

## 上下文预算与压缩

输入预算近似为：**模型上下文容量 − 输出预留 − 协议/工具开销余量**。计数最好使用提供方适配的 tokenizer 或 API 使用量；按中文字数估算只能作为预警。不同模型的上下文容量与输出上限不一定相同。

压缩的优先顺序可以是：删除重复展示 → 大输出只留引用 → 保留最新相关窗口 → 摘要旧调查 → 重新检索必要证据。不要剪断工具请求与结果的配对，或删除影响后续决策的用户约束。

一份可继续工作的摘要应保留：目标、范围、授权边界、已完成事实与来源、已发生副作用、失败尝试、未完成事项、下一步建议。摘要是派生状态；完整日志仍保存原始事实。

## 会话状态与事件日志

至少区分 task、run、step 和 tool call：task 是用户目标，run 是一次执行尝试，step 是一次模型决策加相关执行，call 是一个具体工具调用。项目对 turn/step 的定义不同，不能用一个全局计数器替代全部层次。

UI 的流式增量只用于展示。持久日志保存最终消息、调用、结果、状态改变与产物回执。错误流可以记录为 attempt，供诊断但不一定进入模型历史。**回放不应重新执行历史工具。**它是从日志重建视图与状态。

| 事件 | 持久性建议 | 用途 |
| --- | --- | --- |
| text_delta / progress | 可瞬态 | 快速更新界面 |
| assistant_message | 持久 | 模型实际输出 |
| tool_intent / tool_result | 持久 | 执行证据与恢复 |
| approval_request / decision | 持久并脱敏 | 判断授权范围 |
| checkpoint / summary | 持久 | 压缩与恢复 |
| task_status | 持久 | 判断终态与未完成项 |

日志必须带版本、run ID、事件序号、时间和关联 ID；不要仅依赖墙上时钟排序。持久化可以从 JSONL 起步，复杂查询用 SQLite，但存储实现不应散落到每个工具里。

RIVER 的设计还要求分清 `Session`、业务 `Task`、业务 `Run` 与 Harness 的 `Turn/Step`：一个长期定时 Task 可以触发多次 Run，而一次 Run 内含若干模型步骤和工具调用。调度器确认投递到 Session，只证明触发已送达，不证明交通分析完成；业务状态必须由 Run 的结果与失败原因记录。首期设计优先定时触发，交通事件触发暂缓；监测安全预警不得依赖 LLM 持续在线。

`World State` 保存可查询的专业时空态势，`Result Store` 保存大体量轨迹、预测和数值产物，二者都不等于对话记忆。历史回放还要避免未来数据泄漏：观测发生时间、系统可用时间与预测有效时间要分别记录。

## 恢复、幂等与不确定副作用

最难的问题是：操作已经发生，进程却在写日志之前崩溃。恢复时日志没有成功结果，不能证明操作没发生。RIVER 当前设计优先只读查询和计算，但创建/修改定时任务、外发通知等未来副作用也必须有回执与幂等设计，尤其不能在状态未知时直接重试。

<div class="diagram"><div class="flow"><div class="node">保存 Intent<small>operation ID + 参数</small></div><span class="arrow">→</span><div class="node">执行动作<small>能否幂等？</small></div><span class="arrow">→</span><div class="node">保存 Receipt<small>产物 / 外部 ID</small></div><span class="arrow">→</span><div class="node">恢复核对<small>查询或人工处理</small></div></div><p class="caption">只有 Intent 时，查询结果优先；无法查证的动作保持“不确定”，不能默认成功或失败。</p></div>

对写文件可以用内容摘要、预期旧版本和原子发布；对外部 API 优先使用幂等键；对修改共享资源使用版本条件或 compare-and-swap。不要承诺所有动作都有 exactly-once 效果。网络超时往往只能证明没收到回执，无法证明服务端没执行。

恢复还要重新验证运行环境、工具可用性、插件版本和授权。对 RIVER 来说，还要重新检查 AIS 等观测的可用时间、预测结果有效期和规则版本；历史结果未过期于会话，并不代表仍适用于当前交通态势。旧会话曾获批的动作不必然在新的资源、参数或账号上仍有效。

## 错误、重试与取消

| 错误类型 | 典型处理 | 不应该做 |
| --- | --- | --- |
| 格式/参数错误 | 给出可修复错误，让模型纠正 | 未校验就尝试执行 |
| 429 / 暂时传输失败 | 有上限的退避，尊重服务提示 | 无限高频重试 |
| 权限拒绝 | 停止该动作或选允许的替代 | 通过其他工具绕过 |
| 上下文溢出 | 剪枝或压缩后重建请求 | 原样重发同一个过长请求 |
| 动作结果不确定 | 查证回执或目标状态 | 盲目重做写操作 |
| 用户取消 | 传播信号，清理资源，记录已发生动作 | 最后再跑一次“收尾”危险动作 |

重复无进展检测可以比较工具名、规范化参数、结果摘要与任务状态。相同请求不是永远错误：轮询任务状态可能合理；但每次读取同一文件得到同一结果，又没有新的假设，就应该停止或改变策略。

给每次任务设置步骤、调用、时间和费用上限。费用上限应根据 usage 累积，预留下一次调用可能消耗的额度。设置了 `max_steps` 仍可能因某个工具永久阻塞而卡死，所以工具超时和取消必须另外实现。

## 权限、审批与执行环境

权限不是提示词里的“请小心”。宿主在执行前检查：文件根目录、网络目标、进程权限、账号、资源和动作。审批负责确认某次动作的意图；沙箱负责限制执行能触及的环境。两者作用不同。

为 RIVER-Agent 设计分级权限：默认按任务授权只读查询；Plan Mode 规划阶段的只读限制由 Runtime 策略强制；创建或修改定时任务、发送通知等副作用绑定具体对象并经过授权。系统不自动控制实船，也不发布约束性通航指令。向用户展示实际动作、目标、预期变化和可恢复性，而不是一堆抽象安全标签。

Shell 要清理环境变量，控制进程树、工作目录、资源限制和网络。浏览器工具要处理下载、表单提交和不同账号身份；MCP 服务要最小化 scope。第三方插件属于执行代码，不能靠模型层规则隔离。

Pi 的 README 明确说明没有内置的文件系统/进程/网络/凭据权限限制，默认继承宿主权限；可采用外部容器或沙箱。[Pi 权限说明](https://github.com/earendil-works/pi#permissions--containerization)。DeepSeek Harness 的安全说明将其标为实验性开发者预览，不能视作已审计的生产安全系统。[dsh 安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.zh.md)。

## 防止提示注入与凭据泄露

为所有上下文标注来源：用户、开发者指令、可信 skill、仓库文件、外部网页、工具结果。外部资料中的操作指令属于数据，不能提升为新的开发者政策。标注信任等级有帮助，但不能保证模型永远不受诱导。

更强的控制是让模型无法调用不需要的能力：只读任务不暴露发送工具，检索服务不返回凭据，工作区不挂载个人密钥目录，网络出口限制到必要域。对敏感操作，程序检查明确参数，而不是仅让模型判断“安全吗”。

日志脱敏应覆盖密钥、认证头、个人资料和敏感正文。调试时保存全量请求很方便，也可能造成泄露；因此需要访问控制、保留期限、导出检查和删除机制。长期记忆同样要可审阅、可纠正、可清除。

## 评估：让改进有证据

建立你自己的任务集，而不是只看某个公开排行榜。每条任务包含输入环境、初始状态、用户目标、允许动作、成功断言、预算与失败判定。同一数据集可以比较不同模型、不同 skill、不同工具和不同上下文策略。

建议从 20–30 个覆盖真实工作的小任务起步，这个数量是教学建议。覆盖正常、缺信息、歧义、权限拒绝、工具失败、长上下文、资料冲突和提示注入。重要任务多次运行，报告分布，不只挑最好的一次。

| 指标 | 衡量什么 | 注意事项 |
| --- | --- | --- |
| 任务成功率 | 验收器判定成功的比例 | 验收规则要独立于回答措辞 |
| 工具正确率 | 参数、对象、顺序是否合理 | 应分错误类别 |
| 越权率 | 被执行的违规动作 | 拒绝请求不等于越权执行 |
| 证据完整率 | 关键结论能否回溯 | 链接存在不等于支持结论 |
| 成本与延迟 | 每个成功任务的代价 | 看失败任务和尾部延迟 |
| 恢复成功率 | 中断后是否正确继续 | 不可重复副作用单独统计 |

确定性断言最适合文件和状态；模型裁判可评语义，但需要校准与人工抽样。做消融实验时一次改变一个组件；做模型替换实验时固定 harness。不能看到换模型后分数不涨，就断言模型无作用：任务难度、样本量和验收器也可能限制观察。[原书第 7 章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter7.md)。

## 多 Agent：通用路线中的可选项

多 Agent 是通用 Agent 技术路线中的一种可选架构，适合独立调查、隔离上下文或角色复核。RIVER-Agent 当前设计选择单一中央 LLM Agent，航运专业算法和数据服务不是其他 Agent。除非评估证明拆分能改善独立性、吞吐或验证质量，否则不要把领域服务改造成互相对话的多个 LLM 角色。若其他产品选择多 Agent，先写明独立子任务的输入、输出、权限、预算和交付责任。

一个可评估的通用模式：主 Agent 分配多个只读且互相独立的调查任务 → 子 Agent 返回证据与不确定项 → 主 Agent 合并 → 独立验证。各子任务不能自行扩大授权；总费用要跨任务累积。对 RIVER 的基线应先与单 Agent、同预算、同数据和同工具比较。

共享目录最容易发生并发冲突。可以划分文件所有权、使用隔离工作区，再通过补丁或产物合并。共享上下文提高信息复用，也可能传播同一个错误；相同模型和相同提示得到一致答案，不构成独立证明。[原书第 10 章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter10.md)。
