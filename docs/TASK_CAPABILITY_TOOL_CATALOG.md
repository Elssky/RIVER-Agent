# RIVER-Agent：任务类型、原子能力与工具体系设计

> 版本：v0.1（讨论稿）  
> 状态：**规划与接口设计，非已实现功能清单**  
> 适用项目：[RIVER-Agent](https://github.com/Elssky/RIVER-Agent)  
> 范围：统一中央智能体、自然语言被动响应、定时主动执行、事件触发及持续监测。

本文记录当前讨论形成的 **13 类任务（K01–K13）、23 项原子能力（C01–C23）、24 个逻辑工具（T01–T24）**，以及任务—能力—工具的映射和完整执行案例。所有工具名、字段和执行过程均为**设计建议**，不表示相关 AIS、雷达、预测模型、通知通道或调度服务已经接入、部署或测试通过。

## 1. 设计原则

- **一个中央 Agent**：只由统一中央智能体负责理解任务、规划、调用工具、整合证据与处理执行反馈；专业算法和调度服务不是其他 LLM Agent。
- **触发方式与业务任务分离**：自然语言请求、定时计划和交通事件可触发相同的业务任务；一次性/持续性是独立的任务生命周期属性。
- **任务 → 能力 → 工具**：任务表示目标，原子能力表示解决目标所需的能力，工具表示实际数据访问或计算接口。能力与工具不是一一对应。
- **按需执行**：映射表给出典型依赖与候选工具，不应固化为每次都执行的脚本；中央 Agent 根据状态动态选择、重试或结束。
- **独立验证**：LLM 不直接承担精确风险数值计算；预测、风险计算与规则核查由可验证的专业组件完成。
- **有限自主**：计划配置、工具访问、运行预算及用户通知受权限、时间与安全约束；涉及航行指挥的建议保留人工审核。
- **先建设能力、后系统验证**：现阶段先打通可运行场景，Benchmark 与消融实验后续开展；不将候选机制表述为已证明的贡献。

## 2. 任务模型

### 2.1 三个正交维度

| 维度 | 可选值 | 说明 |
| --- | --- | --- |
| **触发方式** | `user_request`、`schedule`、`event` | 用户请求、定时器、交通监测事件。 |
| **生命周期** | `one_shot`、`continuous` | 单次执行或持续运行，持续任务需终止条件。 |
| **业务类型** | K01–K12；K13 为管理类意图 | 允许多种业务类型组合。 |
| **复杂程度** | 查询、分析、复合决策 | 决定是否需要多步规划。 |
| **输出形式** | 文本、结构化数据、地图、报告、通知 | 根据任务和可用交付通道决定。 |

**K13 不是新的航运专业算法**，而是创建、修改、暂停、取消及查询其他业务任务的管理意图。例如“每天8点预测拥堵”可表示为 K13 + K07。

### 2.2 任务结构（示意）

```json
{
  "task_id": "task_001",
  "trigger": {"type": "schedule", "cron_or_rule": "daily 08:00", "timezone": "Asia/Shanghai"},
  "lifecycle": "continuous",
  "business_tasks": ["K04"],
  "scope": {"area_name": "指定桥区", "area_id": null},
  "parameters": {"prediction_horizon_minutes": 5},
  "notification_policy": {"condition": "verified_high_risk", "channel": null},
  "status": "needs_configuration"
}
```

以上是结构示例，非最终 API Schema。任务创建时若水域未唯一解析、通知渠道或授权方式尚未明确，不得假定任务已经可以自动执行。

## 3. 原子能力集合 C（23 项）

### 3.1 Agent 共性能力

| ID | 能力 | 定义 | 主要实现方式 |
| --- | --- | --- | --- |
| C01 | 自然语言理解 | 识别意图、任务目标、约束、触发条件与输出要求 | 中央 Agent |
| C02 | 时空与实体解析 | 解析时间、航段/桥区边界、船舶身份及其歧义 | Agent + T01/T02 |
| C03 | 动态任务规划 | 根据当前状态选择下一动作、工具和停止条件 | 中央 Agent |
| C04 | 任务状态与短期记忆 | 保存目标、上下文、计划、执行记录及状态 | Agent Runtime + T22 |
| C05 | 证据与结果验证 | 检查时间一致性、来源、数值、规则与候选建议 | 独立验证器 + T19 |
| C06 | 结果生成与交互 | 将可信结果转换为文本、数据、地图或通知内容 | 中央 Agent + 输出组件 |

### 3.2 自主运行、记忆与纠错能力

| ID | 能力 | 定义 | 主要实现方式 |
| --- | --- | --- | --- |
| C07 | 定时任务管理 | 创建、修改、暂停、恢复、取消周期或一次性计划 | 调度服务 + T20 |
| C08 | 事件触发与持续监测 | 订阅事件、持续观察、去重、升级与结束 | 监测服务 + T21 |
| C09 | 长期经验记忆 | 检索并复用经过核验的历史交通事件与分析经验 | 经验库 + T18 |
| C23 | 异常恢复与重规划 | 工具失败、超时、证据不足或验证不通过时调整计划 | Agent Runtime |

### 3.3 航运专业能力

| ID | 能力 | 定义 | 主要工具 |

### 3.4 报告能力

| ID | 能力 | 定义 | 主要工具 |
| --- | --- | --- | --- |
| C22 | 综合报告生成 | 组织周期摘要、历史趋势、事件复盘及风险报告 | T23 |

**能力是可复用的功能定义，并非独立软件服务清单。** C01、C03、C23 等可主要由 Agent 内核实现，无须为每一项能力创建一个外部工具。

| ID | 拟定工具名 | 典型输入 | 核心返回 | 支撑能力 |
| --- | --- | --- | --- | --- |
| T20 | `manage_scheduled_tasks` | 计划、周期、时区、用户授权、操作类型 | 调度配置与任务 ID | C07 |
| T21 | `manage_monitoring_tasks` | 监测对象、事件条件、结束条件、操作类型 | 监测配置与订阅状态 | C08 |

## 5. 任务目录 K：示例、能力和工具的对应关系

### 映射规则

- 业务任务默认依赖 **C01–C06** 的共性能力，但简易查询无需强制多轮规划。
- “**典型工具集合**”是该类任务常见执行的参考集合；实际必要工具取决于请求是区域级、单船级、当前状态还是历史回放。
- “**按需**”表示可能因为数据质量、规则、环境或重规划条件而补充调用。
- 任务类别可以组合，复用数据与计算结果；并非每条自然语言都要单独设计固定工作流。

### K01 — 区域交通态势查询

**自然语言示例：**
1. 现在南京某桥区有多少艘船？
2. 目前哪些航段的船舶密度比较高？
3. 分析当前某交汇区的整体交通情况。

- **专项能力：** C10（AIS 状态）、C13（交通统计）。
- **典型工具：** T01 → T03 → T07。
- **按需工具：** T05（质量检查）、T06（辅助观测）。
- **输出：** 船舶数量、分布、速度/密度及数据时刻。

### K02 — 单船状态与历史轨迹

**自然语言示例：**
1. 查一下这艘船最近30分钟的航行轨迹。
2. 这艘船过去两小时的平均航速是多少？
3. 这艘船刚才经过了哪些航段？

- **专项能力：** C11（轨迹分析），必要时 C02（船舶身份）。
- **典型工具：** T02 → T04。
- **按需工具：** T05（数据质量）、T12（异常行为）。
- **输出：** 历史轨迹、航速统计、经过的水域及观测质量。

### K03 — 多船轨迹预测

**自然语言示例：**
1. 预测这艘船未来5分钟的位置。
2. 预测桥区附近这5艘船的未来轨迹。
3. 哪些船未来10分钟可能进入交汇区？

- **专项能力：** C11、C12、C14。
- **典型工具：** T03 或 T02，配合 T04 → T05 → T08。
- **按需工具：** T01、T06。
- **输出：** 轨迹、预测时间、模型版本、可用的不确定性信息。
- **范围提示：** 10分钟是需求示例，不意味着现有模型已经达到该预测能力。

### K04 — 多船冲突与碰撞风险

**自然语言示例：**
1. 未来5分钟哪些船可能发生冲突？
2. 这两艘船是否存在碰撞风险？
3. 分析某交汇区目前风险最高的船舶。

- **专项能力：** C12、C14、C17。
- **典型工具：** T03/T04 → T05 → T08 → T11 → T19（短时预测风险任务）。
- **按需工具：** T02、T06、T13、T14、T15。
- **输出：** 风险船对、预测冲突、指标依据、规则约束、可信度或证据限制。
- **范围提示：** 对仅要求当前 CPA/TCPA 的问题，可直接使用 T11，无须强制 T08。

### K05 — 船舶异常行为分析

**自然语言示例：**
1. 这艘船为什么突然减速？
2. 找出最近一小时可能发生异常偏航的船舶。
3. 哪些船舶存在超速或异常停航情况？

- **专项能力：** C11、C12、C18。
- **典型工具：** T04 → T05 → T12。
- **按需工具：** T02、T06、T13、T14、T18。
- **输出：** 异常事件和证据、可能原因及未知项。
- **范围提示：** 仅凭运动异常不能断言其真实原因；原因解释须区分事实和假设。

### K06 — 航道拥堵现状分析

**自然语言示例：**
1. 目前哪个航段最拥堵？
2. 为什么最近30分钟该航段船速持续降低？
3. 某桥区是否已经形成通航瓶颈？

- **专项能力：** C10、C13、C16。
- **典型工具：** T01 → T03 → T07 → T10。
- **按需工具：** T09、T14、T05。
- **输出：** 当前拥堵程度、关键航段、可能的瓶颈因素。

### K07 — 交通流与拥堵预测

**自然语言示例：**
1. 预测未来一小时某航段的船舶流量。
2. 未来两小时哪些航段可能出现拥堵？
3. 上游交通增长会不会影响下游通行？

- **专项能力：** C13、C15、C16。
- **典型工具：** T01、T07、T09。
- **按需工具：** T10、T14、T05。
- **输出：** 未来流量、趋势和拥堵分析。
- **范围提示：** 预测时间尺度需与所用模型的有效时域一致。

### K08 — 航行规则与通航条件

**自然语言示例：**
1. 某桥区目前有什么通航限制？
2. 这艘船现在能否通过指定航段？
3. 最近有哪些新发布的航行通告？

- **专项能力：** C19。
- **典型工具：** T01 + T13/T14；涉及可通行性判断时再调用 T15。
- **按需工具：** T02、T06。
- **输出：** 适用规则、通告、限制、有效时间与依据。

### K09 — 通航事件影响分析

**自然语言示例：**
1. 这次临时封航会影响哪些船舶？
2. 某桥区施工会不会造成周边航段拥堵？
3. 水位下降可能影响哪些船舶通行？

- **专项能力：** C10、C15、C16、C19。
- **典型工具：** T01、T03、T14、T15。
- **按需工具：** T06、T07、T09、T10。
- **输出：** 事件影响范围、受影响船舶、交通变化预期。

### K10 — 航路规划与推荐（第二阶段）

**自然语言示例：**
1. 这艘船从当前位置到目标港区有哪些可行航路？
2. 考虑当前航道限制，推荐一条低风险航路。
3. 比较两条候选航路的风险与预计通行时间。

- **专项能力：** C17、C19、C20；复杂场景可用 C14。
- **典型工具：** T02、T13、T14、T15、T16、T19。
- **按需工具：** T08、T11、T09。
- **输出：** 经约束检查的候选路线与比较结果，不是直接船舶控制指令。

### K11 — 交通组织与协同优化（第二阶段）

**自然语言示例：**
1. 未来10分钟进入桥区的船舶应如何安排通行顺序？
2. 如果上游船流持续增加，应该如何调整交通组织？
3. 如何降低交汇区多船冲突与等待时间？

- **专项能力：** C13、C14、C15、C17、C19、C21。
- **典型工具：** T03、T07、T11、T17、T19。
- **按需工具：** T08、T09、T14、T15。
- **输出：** 交通组织候选方案、可行性、约束与预计影响。

### K12 — 综合分析与报告

**自然语言示例：**
1. 生成今天某航段的交通运行报告。
2. 总结过去一周的异常事件和拥堵情况。
3. 综合分析某交汇区的运行问题并提出管理建议。

- **专项能力：** C22；依据报告主题组合 C13、C16、C17、C18、C19。
- **典型工具：** T23 + 报告主题所需数据查询/分析工具（常见 T03/T04/T07）。
- **按需工具：** T09、T11、T12、T14。
- **输出：** 结构化或文本报告，含范围、时刻、来源和限制。

### K13 — 自动任务管理（跨业务类型）

**自然语言示例：**
1. 每天早上8点分析某航段的交通运行情况。
2. 持续监测这艘船，发生风险时通知我。
3. 暂停每小时执行的桥区风险分析任务。

- **专项能力：** C07、C08、C04、C23。
- **典型工具：** T20（定时计划）或 T21（持续监测），查询运行状态时用 T22。
- **按需工具：** T24（通知）及所绑定业务任务的工具。
- **输出：** 任务配置、运行状态、后续执行结果。
- **特别说明：** 用户说“每天8点预测拥堵”，解析为 **K13 + K07**；说“持续关注某船碰撞风险”，解析为 **K13 + K04**。不得仅凭保存任务定义就声称已完成业务分析或通知发送。

## 6. 触发方式如何复用业务任务

| 请求示例 | 触发 | 生命周期 | 任务组合 |
| --- | --- | --- | --- |
| 现在分析桥区交通态势。 | 用户请求 | 一次性 | K01 |
| 每15分钟预测一次该航段拥堵。 | 定时 | 持续 | K13 + K07 |
| 每天生成一份交通运行报告。 | 定时 | 持续 | K13 + K12 |
| 发现潜在冲突时自动分析风险。 | 事件 | 持续订阅、每事件一次执行 | K13 + K04 |
| 出现异常停航时分析可能原因。 | 事件 | 持续订阅、每事件一次执行 | K13 + K05 |
| 新限航通告发布后评估影响。 | 事件 | 持续订阅、每事件一次执行 | K13 + K09 |
| 关注某船直至其驶离桥区。 | 用户创建监测 | 持续、有结束条件 | K13 + K02/K04 |
| 每天分析交通态势和拥堵并出报告。 | 定时 | 持续 | K13 + K01 + K07 + K12 |

**任务配置**与每次**任务执行实例**必须区分：`task_id` 标识持久化任务，`run_id` 标识某次运行。对于同一持续任务，可有多个事件触发的运行实例。

## 7. 详细案例：自然语言创建定时风险分析任务

### 7.1 用户输入

> 每天早上8点，分析南京某桥区未来5分钟的船舶碰撞风险。如果发现高风险船舶，通知我，并说明风险原因和建议。

这句话包含两个阶段：

- **任务创建阶段**：解析意图、区域、时区、运行周期、风险条件与通知方式。
- **每次运行阶段**：在执行时刻采集当前数据、完成风险分析、验证结论，并在满足条件时通知。

### 7.2 任务创建：自然语言 → 任务定义

1. **C01** 识别 `create_task`；业务任务为 K04，管理任务为 K13。
2. **C02 + T01** 将“南京某桥区”解析为水域实体；若无法唯一匹配，则要求明确水域，不能任意选择。
3. **C03** 确定需要每天8:00（本例按北京时间 `Asia/Shanghai`）、预测5分钟、仅验证为高风险时通知。
4. **C07 + T20** 在用户授权、区域和通知配置有效后保存定时计划。
5. **C04 + T22** 记录并展示任务状态；创建成功并不意味着当日已经运行。

**任务结构示意（假设尚未完成区域与通知配置）：**

```json
{
  "task_id": "task_001",
  "intent": "create_task",
  "business_tasks": ["K04", "K13"],
  "trigger": {
    "type": "schedule",
    "recurrence": "daily",
    "time": "08:00",
    "timezone": "Asia/Shanghai"
  },
  "scope": {
    "area_name": "南京某桥区",
    "area_id": null
  },
  "prediction_horizon_minutes": 5,
  "notification_condition": "verified_high_risk",
  "notification_channel": null,
  "status": "needs_configuration"
}
```

只有补齐必要信息并成功持久化之后，才能进入有效调度状态。用户没有给出具体桥区或通知渠道时，不假定已完成配置。

### 7.3 每天8:00：调度器唤醒中央 Agent

调度服务为这次执行生成 `run_id`，向中央 Agent 提供固定的分析时刻、区域、任务参数和已知的权限信息。**LLM 不需要自己一直在线数秒，也不负责充当计时器。**

本次运行可用的专项能力包括：

- C10 船舶状态、C11 历史轨迹、C12 质量评估；
- C14 多船预测、C17 冲突风险计算、C19 规则核查；
- C05 独立验证、C06 结果输出；
- C03/C04/C23 用于规划、状态及异常处理。

**一种典型执行路径：**

| 步骤 | 判断或动作 | 能力 | 逻辑工具 |
| --- | --- | --- | --- |
| 1 | 获取区域边界和船舶列表 | C02、C10 | T01、T03 |
| 2 | 获取分析所需的船舶运动历史 | C11 | T04 |
| 3 | 检查数据缺失、跳变与更新延迟 | C12 | T05 |
| 4 | 对满足要求的目标船舶预测未来5分钟轨迹 | C14 | T08 |
| 5 | 计算船对冲突及风险指标 | C17 | T11 |
| 6 | 按任务需要检索并判断桥区规则及通告 | C19 | T13、T14、T15 |
| 7 | 检查输入、预测、风险、规则及建议证据 | C05 | T19 |
| 8 | 满足通知条件时发送提示 | C06 | T24 |
| 9 | 保存本次运行结果，等待下次触发 | C04 | 任务运行状态存储 / T22 |

该表描述**典型路径**，不是强制执行序列；C03 可根据请求和反馈省略不必要的工具或补充调用其他工具。

### 7.4 动态重规划：发现 AIS 更新延迟

以下为**虚构示例**，只用于说明逻辑。

假设 T03 返回船舶 A、B、C，T05 发现 C 的最后一次 AIS 观测距离当前已有3分钟。

- **若存在有效辅助观测**：中央 Agent 可调用 T06 查询可用雷达等信息，更新数据质量判断，再决定是否执行 T08/T11。
- **若没有有效辅助观测**：不把过时位置当成实时真实位置；可以执行允许的不确定性分析，或对相关船舶返回“证据不足”。
- **若工具失败/时间预算不足**：C23 触发有限次数的恢复、重规划或降级，不无限尝试。
- **无论哪条分支**：基础风险监测与必要的及时告警不应等待 LLM 全部推理完成。

这种重规划的核心是：Agent 在任务目标不变的情况下，依据工具返回的**状态、时间、质量和可用性**重新选择行动。

### 7.5 风险结果与独立验证

假设 T08/T11 对 A、B 返回以下**纯示例数据**：

| 指标 | 虚构值 |
| --- | --- |
| 预计接近/冲突时间 | 约3分钟后 |
| DCPA | 0.08 nmi |
| TCPA | 180 s |
| 相关对象 | 船舶 A、B |
| 候选判定 | 需要进一步核验的高风险候选 |

**不能仅凭这些假设数值断言真实高风险**。应由 T19 检查观测时间、风险计算、适用航段规则和方案约束；真正的风险阈值与分类口径需要单独研究并确认。

- **验证通过、符合通知条件**：由 T24 发出带时间、证据与限制说明的通知，并记录实际发送结果。
- **验证未通过**：明确报告数据或规则不足；不把未经确认的候选高风险当成确定结论。
- **无需通知**：归档运行记录，等待下一个周期。

**通知文本示例（虚构）：**

> 某桥区08:00的交通分析发现船舶 A 与 B 存在需要关注的潜在会遇风险。预计接近时间约为3分钟后。建议值班人员结合实时交通态势进一步核查两船动态。附：分析时间、数据来源、预测与验证记录。

### 7.6 运行后的状态与记忆

| 对象 | 应保存的内容 |
| --- | --- |
| `task_id` | 每天8点运行的计划定义及授权信息 |
| `run_id` | 本次运行起止时间、状态及异常 |
| 工具执行历史 | 工具名、版本、输入/输出摘要、来源与错误 |
| 任务短期状态 | 当前计划、已完成步骤、未解决事项 |
| 分析结果 | 风险对象、证据、预测时域、规则和验证状态 |
| 通知状态 | 是否满足通知条件、渠道与实际发送回执 |
| 长期经验 | 仅写入符合核验与权限要求的事件记录 |

这样用户以后问“昨天早上那次风险分析发现了什么”，系统可依据 `task_id`/`run_id` 查询历史记录，而不是依赖 LLM 的聊天记忆。

## 8. 持续监测案例：任务生命周期不同，复用相同专业工具

**自然语言：**

> 从现在开始关注船舶 A，直到它离开指定桥区。如果风险升级，及时分析并通知我。

- **任务组合**：K13 + K02 + K04。
- **创建阶段**：T02 唯一解析船舶，T01 解析桥区，T21 创建具有结束条件的监测订阅。
- **常规监测**：监测服务按可用数据更新目标状态；并非每次 AIS 更新都调用 LLM。
- **风险变化事件**：触发中央 Agent，视情况调用 T04/T05/T08/T11/T19，必要时 T24。
- **结束条件**：确认目标离开指定监测水域、用户取消任务或到达设定的超时条件。
- **防重复通知**：相同事件在短时间内不应重复发送，风险等级升级可以产生新事件。

**持续监测是任务生命周期；主动事件是触发方式**。二者可以同时存在，不是两个互斥的 Agent 类型。

## 9. 首批建设范围与依赖

| 阶段 | 建议先覆盖的任务 | 工程重点 |
| --- | --- | --- |
| **P0：Agent 内核与基础查询** | K01、K02、K08（基础规则查询） | 任务解析、状态机、数据查询、工具注册、基本验证 |
| **P1：预测、风险与主动服务** | K03、K04、K05、K06、K07、K12、K13 | 预测/风险服务、调度与监测、持久化执行、报告与通知 |
| **P2：复杂决策协同** | K09、K10、K11 | 动态通航影响、航路优化、区域协同决策 |

**建议首先贯通的示范场景：** “分析指定桥区未来5分钟多船冲突风险，提供可追溯依据”。其后加上定时和持续运行能力。阶段划分是研发优先级，不代表后续能力已经实现。

## 10. 待明确事项

1. **AIS 数据可用性**：是否具备分钟级多船原始轨迹、明确时间戳及可研究的航段。
2. **辅助数据权限**：雷达、气象、水文、船闸和桥区信息的获取方式及更新频率。
3. **预测模型**：短时多船预测与已有航段流量预测的部署接口和有效时域。
4. **风险定义**：风险阈值、风险分级、规则来源、独立验证口径。
5. **调度与通知**：部署环境、时区、持续任务存储、通知渠道、用户授权与重试策略。
6. **工具 Schema**：各接口的参数、输出、错误分类和权限控制。
7. **评价体系**：任务与事件数据、Benchmark、独立验证和对照实验（后续开展）。

## 11. 后续接口设计建议

建议继续形成三个机器可读注册表和统一执行状态：

- **Task Registry**：`task_id/type`、输入参数、触发方式、生命周期、必备能力、输出模式与完成条件。
- **Capability Registry**：`capability_id`、前置条件、依赖能力、可用工具、质量条件。
- **Tool Registry**：`tool_id`、Schema、权限、资源成本、超时、失败类型、来源与版本。
- **Task State**：目标、可用证据、当前计划、执行历史、错误、预算、是否完成/继续/等待确认。

研究目标是让中央 Agent **基于任务和证据动态选择能力与工具**，而不是把 K01–K13 分别编码成不可改变的固定流程。
